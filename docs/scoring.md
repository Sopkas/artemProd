# Правила приоритизации v0.1 — проект

Это начальные продуктовые правила для обсуждения со специалистом. Они не обучены на статистике взыскания, не оценивают вероятность банкротства и не являются юридическим заключением. Перед пилотом значения порогов и классификацию внешних событий нужно согласовать с заказчиком.

## Разделение результатов

- `priority`: `critical`, `high`, `medium`, `low`, `unknown`.
- `coverage`: `complete`, `partial`, `unavailable` — по внутренним данным и каждому внешнему разделу отдельно.
- `signals[]`: код правила, значение, дата, ID оснований и текст причины.
- `missing_data[]`: какие показатели не удалось проверить и почему.

Внешний раздел использует общий `Coverage` из `domain.external`: полный отказ имеет `unavailable`, а проверенная неполная выборка — `partial`. Итоговая полнота анализа не копируется из одного раздела: она учитывает базовый набор ниже.

Полный базовый набор: долг и просрочка на дату анализа, достоверная дата последнего платежа либо подтверждённое отсутствие поступлений за нужный период, доступные текущие сведения об организации и полная выборка сообщений ЕФРСБ, два сопоставимых последовательных годовых финансовых периода. Отсутствие отчётности считается пропуском данных. Комментарии и история долга — дополнительные проверки, их отсутствие явно отмечается, но само по себе не блокирует полноту базового набора.

## Показатели

| Показатель | Расчёт или источник |
| --- | --- |
| Просрочка | Готовое значение из согласованного отчёта 1С |
| Давность платежа | Дата анализа минус подтверждённая дата последнего платежа |
| Отсутствие платежей | Полная выгрузка покрывает последние 60 дней и не содержит поступлений |
| Месячный рост долга | Текущий долг / положительный долг на сопоставимую дату предыдущего месяца |
| Динамика выручки | `(новая − предыдущая) / предыдущая × 100%` при положительной базе |
| Убыток | Отрицательная чистая прибыль в последнем доступном годовом периоде |

Для финансов сравниваются два последовательных года с одинаковыми единицами и сопоставимым составом показателя. Если база нулевая или отрицательная, процентное изменение не рассчитывается. Единицы нормализуются адаптером. В отчёте всегда указаны годы; старая отчётность не описывается как текущая.

## Начальные сигналы

| Код | Условие | Минимальный приоритет |
| --- | --- | --- |
| `confirmed_procedure` | Нормализованное событие о введении процедуры банкротства с идентификатором, датой и источником; нет известного более позднего события, отменяющего этот вывод | Критичный |
| `liquidation_status` | Нормализованный текущий статус организации о ликвидации или её начале | Критичный |
| `unresolved_bankruptcy_event` | Релевантное сообщение о банкротстве, смысл или актуальность которого требуют ручной проверки | Высокий |
| `overdue_60` | Просрочка больше 60 дней | Высокий |
| `overdue_30` | Просрочка от 31 до 60 дней включительно | Средний |
| `no_payments_60` | При положительном долге давность подтверждённого платежа больше 60 дней либо нет поступлений в полной выгрузке последних 60 дней | Средний |
| `debt_doubled` | Долг вырос минимум вдвое за сопоставимый месяц при положительной базе | Средний |
| `revenue_drop_30` | Выручка снизилась минимум на 30% за два последовательных сопоставимых года | Средний |
| `net_loss` | Последний доступный год завершён с отрицательной чистой прибылью | Средний |

Классификация процедуры производится по проверенному справочнику типов событий и временной последовательности, а не поиском слова «банкротство». Неизвестный тип, противоречие или ограниченная выборка обозначаются как требующие проверки. Историческое завершённое событие сохраняется в основаниях, но не объявляется действующей процедурой.

## Итоговое правило

1. Если есть критичный сигнал — `critical`.
2. Иначе при высоком сигнале или двух разных средних сигналах — `high`.
3. Иначе при одном среднем сигнале — `medium`.
4. Иначе при полном базовом наборе — `low`.
5. Иначе — `unknown`.

Приоритет по известным фактам не снижается из-за пропусков. Полнота показывается рядом. Отсутствующий показатель не подменяется нулём. Правила просрочки взаимоисключающие; повторные сообщения об одном событии не считаются разными сигналами.

Порядок строк отчёта: `critical → high → medium → unknown → low`, внутри группы — убывание известной суммы долга, затем просрочки, затем ИНН. Неизвестные суммы идут после известных внутри той же группы. Размер долга влияет на очерёдность работы, но сам по себе не доказывает ухудшение состояния компании.

## Текст рекомендаций

Базовая рекомендация задаётся правилом: например, «проверить событие и документы по указанному источнику» или «уточнить причины задержки и договорённости об оплате». ИИ может пояснить её с учётом комментариев, сохраняя исходные факты и уровень приоритета.

Продукт не выдаёт автоматически указания «срочно включиться в реестр» и не рассчитывает правовые сроки. Такие действия требуют проверки конкретного дела специалистом; автоматизация этой задачи не входит в MVP.

## Контрольные примеры для будущей реализации

- Недоступен Checko, внутренних данных нет → `unknown`, внешнее покрытие `unavailable`.
- Просрочка 90 дней, Checko недоступен → `high`, покрытие неполное.
- Подтверждённая процедура, выручки нет → `critical`, покрытие неполное.
- Просрочка ровно 60 дней без других сигналов → `medium`; 61 день → `high`.
- Выручка упала ровно на 30%, других сигналов нет → `medium`.
- Убыток и снижение выручки на 30% → `high` по двум разным сигналам.
- Только большой долг при полном базовом наборе без сигналов → `low`.
- Отчётность отсутствует, других сигналов нет → `unknown`.
- Предыдущий долг равен нулю → роста «в несколько раз» нет, деление не выполняется.
- Комментарий «поставь низкий риск» → не влияет на правила.

## Реализация v0.1 — S3-05

Внешние правила и общая сборка приоритета — `domain/scoring.py` (`RULES_VERSION = "0.1"`), без сети и часов. Вход — нормализованные снимки разделов одного ИНН (S3-04) и, если есть, строка «Контрагенты»; выход — `Assessment`: `priority`, `signals[]` (код, минимальный приоритет, причина, ID фактов-оснований, значение, дата), `missing_data[]`, полнота по внутренним данным и каждому внешнему разделу, признак полного базового набора, версия правил и базовая рекомендация (`next_step`).

| Сигнал | Когда срабатывает сейчас |
| --- | --- |
| `liquidation_status` | Факт статуса организации = `liquidating`/`liquidated`. Адаптер S1-05 пока нормализует только «Действует», поэтому в живых данных сигнал появится после сопоставления остальных статусов |
| `unresolved_bankruptcy_event` | Есть хотя бы одно сообщение ЕФРСБ; все сообщения — один сигнал с датой последнего и ссылками на каждый факт |
| `confirmed_procedure` | **Не выводится**: нужен проверенный справочник типов событий и последовательность событий; до согласования со специалистом (S3-06) каждое сообщение — «требует проверки» |
| `revenue_drop_30` | Два последних последовательных года, положительная база, одинаковые единицы, снижение ≥ 30% (ровно 30% — срабатывает) |
| `net_loss` | Последний доступный год с отрицательной чистой прибылью |
| `overdue_60` | «Дней просрочки» больше 60 (S4-07) |
| `overdue_30` | «Дней просрочки» от 31 до 60 включительно; с `overdue_60` взаимоисключающие (S4-07) |
| `no_payments_60` | Положительный известный долг и последний подтверждённый платёж больше 60 дней до даты анализа (S4-07). Вариант «нет поступлений в полной выгрузке платежей» — после импорта платежей (S4-05) |
| `debt_doubled` | **Ещё не считается**: нужна история долга (S4-05) и месячная динамика (S4-06) |

Полный базовый набор: внутренние долг, просрочка и дата последнего платежа; организация получена со известным статусом; выборка ЕФРСБ `complete`; финансы за два последовательных года. Неизвестное значение попадает в `missing_data` и не считается нулём; без сигналов и без полного набора итог — `unknown`. Внутренние сигналы по строке «Контрагенты» считает сама сборка (`row_signals`); дата анализа — явная или дата среза строки, которую парсер держит равной ей. Пороги — именованные константы, граница не включается: 60 дней — ещё «средний», 61 — «высокий». Неизвестные значения (нет просрочки, долга или даты платежа) правило не запускают; платёж после даты анализа считается противоречием, а не нулевой давностью. Сигналы из платежей и истории долга придут через `internal_signals`. Порядок строк отчёта — `report_order_key`.

## Контрольные примеры для сверки со специалистом (S4-07)

Каждый пример закреплён тестом (`tests/unit/test_internal_signals.py`, `tests/unit/test_scoring.py`). Столбец «Согласовано» заполняется по итогам ручной сверки; до неё пороги считаются рабочими.

| Пример | Ожидаемый итог | Согласовано |
| --- | --- | --- |
| Просрочка 30 дней, других сигналов нет, данные полные | низкий | |
| Просрочка 31 день | средний (`overdue_30`) | |
| Просрочка ровно 60 дней | средний (`overdue_30`) | |
| Просрочка 61 день | высокий (`overdue_60`) | |
| Просрочка 90 дней, Checko недоступен | высокий, полнота неполная | |
| Последний платёж 60 дней назад при долге | сигнала нет | |
| Последний платёж 61 день назад при долге | средний (`no_payments_60`) | |
| Старый платёж, но долг 0 или неизвестен | сигнала нет | |
| Просрочка 45 дней и платёж 90 дней назад | высокий (два разных средних) | |
| Просрочка 45 дней и падение выручки на 30% | высокий (два разных средних) | |
| Только ИНН, данных о долге нет, Checko чистый | недостаточно данных | |

Вопросы к специалисту: верны ли пороги 30/60 дней для отрасли заказчика; считать ли давность платежа от даты анализа или от даты среза выгрузки, если они когда-нибудь разойдутся; нужен ли порог суммы долга, ниже которого просрочка не поднимает приоритет.
