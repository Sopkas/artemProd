# Провайдер ИИ-объяснений — интерфейс и подмена (S5-01)

Состояние: 23.09.2026. Интерфейс согласован с B в #36. **Провайдер выбран — агрегатор [polza.ai](https://polza.ai)** (решение Андрея 23.09.2026), клиент подключён: `AI_PROVIDER=polza`. По умолчанию остаётся `off`; `stub` — для локальных проверок без сети. Открытым остаётся одно: какие данные заказчик разрешает отправлять наружу (см. «Что уходит провайдеру») и лимит расходов.

## Интерфейс провайдера

```python
class RecommendationProvider(Protocol):
    name: str      # "stub", позже — имя реального провайдера
    model: str     # точная версия модели; попадает в версию сохранённого объяснения
    async def explain(self, request: Request, limits: AiLimits) -> AiAnswer
```

- `Request` — из `domain/ai_context.build_request`: инструкция, контекст (`dict`, готов к JSON), версии.
- `AiLimits(timeout_seconds=30, max_request_chars=40_000, max_output_tokens=800)` — лимиты одного запроса; полная политика (повторы, бюджет на проверку, выключатель) — S5-03.
- `AiAnswer(text, provider, model, input_tokens, output_tokens, latency_seconds)` — ответ **как пришёл** плюс стоимость. Провайдер ответ не разбирает.
- Ожидаемые отказы — `AiUnavailable(code, message)` с кодом `unavailable | timeout | rate_limited | refused | budget`; ошибки программирования — обычные исключения (воркер зафиксирует проверку как `failed`).
- Провайдер **не логирует** тело запроса и ответ: там данные заказчика.

`request_explanation(provider, context, limits)` → `ExplanationOutcome(provider, model, versions, answer, explanation | rejected | error)`; `status` — `accepted`, `rejected:<код S5-06>`, `unavailable:<код>`. Запрос больше `max_request_chars` наружу не уходит (`unavailable:budget`). `versions = "<provider>:<model>:i<инструкция>:c<контекст>:s<схема ответа>:r<правила>"` — ключ хранения в S5-02: любая смена версии = новый ключ.

## Хранение ответов (S5-02)

Конвейер (`analysis_pipeline._explain`) после расчёта оценок строит контекст каждой организации (`build_context(..., reference="row-N")`, комментарии — только при `AI_SEND_COMMENTS=true`), спрашивает провайдера через `request_explanation` и сохраняет ответ шагом `(ИНН, "explanation", versions)` — `application/explanations.StoredExplanation`: статус, версии, провайдер/модель, ссылка, сырой текст ответа, токены и задержка, принятое объяснение или код отклонения. Сохраняются **принятые и отклонённые** ответы (окончательные); недоступность модели шага не оставляет — следующий прогон может спросить снова (границы — S5-03).

Правила:
- ключ включает все версии (`provider:model:i<инструкция>:c<контекст>:s<схема>:r<правила>`): смена любой — новый ключ, старое остаётся в истории;
- возобновлённая проверка и повторный захват читают шаг и модель не зовут; повторная выдача отчёта (`/report`) конвейер не запускает вовсе — ИИ не вызывается заново;
- принятое объяснение связано с оценкой через `ReportRow.explanation`, версия — в «О проверке» (`ReportMeta.ai_version`: «stub stub-1; контекст 1, инструкция 1»); вывод текста объяснения в отчёт — S5-04;
- шаги живут в хранилище проверки и удаляются с ней по сроку хранения (S6-02).

## Лимиты, повторы, бюджет и выключатель (S5-03)

`application/ai_guard.GuardedRecommendationProvider(inner, AiPolicy)` оборачивает любой провайдер (как guard источников в S3-02); `runtime/ai.py` всегда возвращает провайдера в обёртке.

| Что | Настройка | По умолчанию | Поведение |
| --- | --- | --- | --- |
| Выключатель | `AI_PROVIDER=off` | `off` | Провайдера нет, конвейер модель не зовёт, отчёт — рекомендация по правилам |
| Таймаут вызова | `AI_TIMEOUT_SECONDS` | 30 | `asyncio.wait_for` вокруг вызова → `timeout` |
| Повторы | `AI_MAX_RETRIES` | 1 | Один основной вызов и максимум один повтор при `timeout`/`unavailable`/`rate_limited`, пауза 2 с × попытка; `refused`/`budget`/`truncated` не повторяются |
| Размер запроса | `AI_MAX_REQUEST_CHARS` | 24 000 (≈ 6 000 токенов) | Больше — `budget`, наружу не уходит |
| Размер ответа | `AI_MAX_OUTPUT_TOKENS` | 1 000 | Передаётся провайдеру в `AiLimits` |
| Бюджет проверки | `AI_RUN_REQUEST_LIMIT` / `AI_RUN_TOKEN_LIMIT` / `AI_RUN_TIME_LIMIT_SECONDS` | 100 / 400 000 / 600 | `AiBudget` на всю проверку: запросы (повторы считаются), токены `input+output` по счёту провайдера, срок; по исчерпании остальные организации получают `budget` **без вызова модели** |

Проверка при этом **завершается**: отчёт строится, у организаций без пояснения — рекомендация правил, итог `partial` с причиной «Пояснений ИИ нет у N организаций», та же строка в уведомлении Telegram; `RunSummary.explanations_missing` считается только при настроенном провайдере. Ответ, отклонённый проверкой, — тоже «нет пояснения».

Денежный лимит — производная от токенов и тарифа выбранного провайдера: до выбора провайдера задавать `AI_RUN_TOKEN_LIMIT` из его прайса нельзя, стартовое значение — инженерное. Замер стоимости на реальных ответах — S6-05.

## Структурированный ответ и шаблон в отчёте (S5-04)

`domain/explanation.py`: `explain_row(assessment, explanation, status) → RowExplanation(text, source, note, promises)`. Принятый ответ модели идёт в отчёт как есть (`source="ai"`), обещания оплаты — «до ДД.ММ.ГГГГ (запись INT-1)». Без него — `template_explanation(assessment)`: приоритет, сработавшие сигналы, следующий шаг правил, чего не хватает — **только то, что есть в оценке**, ничего нового. `note` объясняет, почему текста модели нет: «ответ модели отклонён проверкой (код)», «лимит ИИ на проверку исчерпан», «модель не ответила в срок», «модель недоступна», «провайдер отклонил запрос», «ответ модели обрезан лимитом длины».

В Excel: «Приоритеты» — колонки «Пояснение» («ИИ: …» / «По правилам: … (пояснение ИИ недоступно: …)») и «Обещания оплаты»; «Качество данных» — строка «Пояснение ИИ недоступно» по каждой такой организации; «О проверке» — «Пояснения ИИ: принято N, отклонено проверкой M, недоступно K». Недоступная модель или отклонённый ответ отчёту не мешают: он строится всегда, итог `partial` с числом организаций без пояснения (S5-03).

## Подмена (`AI_PROVIDER=stub`)

`StubRecommendationProvider(script=default_answer, delay_seconds=0, failure=None)`:

- `default_answer` строит ответ только из слов запроса — метка приоритета и `next_step` правил, `grounds` = ID оснований сигналов, обещаний нет — поэтому он проходит проверку S5-06 на всех демосценариях (тест).
- `script` — любой текст (тест на отклонение), `delay_seconds` больше `timeout_seconds` → `timeout`, `failure` — заданный `AiUnavailable`.
- `requests` — что было отправлено, для тестов «в запросе нет ИНН/чужих данных».

## Реальный провайдер — polza.ai (`AI_PROVIDER=polza`)

Разведка и замеры сделаны 23.09.2026 с машины разработчика A по документации и живыми запросами; Андрею сервис из-за границы недоступен.

**Доступ.** База `https://polza.ai/api/v1`, метод `POST /chat/completions`, заголовок `Authorization: Bearer <ключ>`. API совместим с OpenAI (можно было бы взять их SDK; мы этого не делаем — клиент на `aiohttp`, как адаптер Checko, лишняя зависимость не нужна). Ключ — только в окружении, `AI_API_KEY`, как `CHECKO_API_KEY`; в репозиторий и в задачи не попадает.

**Ответ.** В `usage` приходят `prompt_tokens`, `completion_tokens` и **цена вызова в рублях** (`cost_rub`) — бюджет S5-03 считается по фактическим числам провайдера, а не по нашей оценке. Клиент пишет в журнал только арифметику: модель, токены, рубли, секунды; ни запрос, ни ответ не логируются.

**Коды ошибок провайдера** (`{"error": {"code", "message", "trace_id"}}`) переведены в наши: 400/401/403/404 → `refused`, 402 «недостаточно средств» → `budget` (повторять бессмысленно), 408 → `timeout`, 429 → `rate_limited`, 5xx и «нет доступных провайдеров» → `unavailable`. Текст провайдера пользователю не показывается и в сообщение не переносится: в нём может быть адрес и ключ.

**Строгая схема ответа.** Модели, у которых в каталоге есть `structured_outputs`, принимают `response_format: json_schema` — и это ровно та схема, которую потом проверяет S5-06. Больше того, клиент подставляет в схему **перечень допустимых `grounds`** — ID значений, фактов и взаимодействий именно этого контекста, — поэтому выдумать основание модель не может. Это не теория: первый же живой ответ сослался на `revenue_drop_30` (код сигнала, а не ID факта), и проверка отклонила объяснение целиком.

**Параметры запроса — по каталогу модели (26.09.2026).** Запрос, подходящий одной модели, другой не подходит. Из 331 чат-модели каталога `max_tokens` принимают все. `temperature` не принимают 90, и это самые новые (`gpt-5.x`, `gpt-6-*`, `claude-opus-5.x`, `gemini-3.x-flash`): на неё они отвечают 400, а у нас это `refused`. `response_format` не принимают 88. Рассуждают до ответа 179, и на рассуждение уходит тот же `max_tokens`. Поэтому клиент при первом вызове читает запись модели в публичном каталоге (`GET /api/v1/models/<id>`, без ключа, не дольше 15 с из таймаута вызова) и запоминает её до конца процесса:

- `temperature: 0` — только если модель его принимает;
- `reasoning: {"effort": "low"}` — если модель рассуждает (`reasoning` в `supported_parameters`). Задача — объяснить уже данные факты, а не решать что-то. Низкий уровень держит рассуждающую модель внутри лимита ответа и цены. `reasoning_effort` на верхнем уровне тела polza не читает, а уровень, которого модель не знает, нормализует или отбрасывает без ошибки;
- схема ответа — если её просит настройка **и** модель принимает `response_format`, иначе формат спрашивается словами, как при `AI_RESPONSE_FORMAT=none`.

Если каталог не ответил, уходит только то, что принимают все: без `temperature` и `reasoning`, схема — по настройке. Каталог спрашивается снова со следующим вызовом. В журнал пишется одна строка `ai_catalog` с тем, что прочитано.

**Обрезанный ответ** (`finish_reason=length`) получает свой код `truncated`. Такое бывает и с пустым текстом, когда рассуждающая модель потратила весь лимит на рассуждение. Он не повторяется: тот же запрос остановится на той же длине и будет оплачен ещё раз. Его цена всё равно записывается в бюджет проверки (`AiUnavailable.spent`), так что рублёвый лимит видит и деньги, потраченные без ответа.

**Модели.** Каталог — `GET /api/v1/models` (414 позиций на 23.09.2026), цены в рублях за миллион токенов. Замер на одном синтетическом контексте (7 068 символов запроса, температура 0):

| Модель | Принято проверкой | Время | Цена одного объяснения | Примечание |
| --- | --- | --- | --- | --- |
| `openai/gpt-4.1-mini` | **5 из 5** | 7–34 с | 0,06–0,11 ₽ | значение по умолчанию |
| `google/gemma-3-27b-it` | 2 из 2 | 15–59 с | ≈ 0,026 ₽ | дешевле, замеров мало |
| `openai/gpt-4o-mini` | **0 из 3** | 18–49 с | ≈ 0,025 ₽ | нарушает правило 2 инструкции: пишет числа, которых нет во входных данных («более 90 дней») |

На 50 организациях объяснения по умолчанию стоят порядка 3–6 ₽ — на фоне суточного лимита Checko это не ограничение.

**Что из этого следует:**

- **Лучшее соотношение — `gemini-3.5-flash-lite`.** Принято 8 из 9, 6 без замечаний, 0,11 ₽ за объяснение (≈ 5,5 ₽ на 50 организаций), 5 с. Модель принимает `temperature`, так что тот же контекст даёт то же объяснение. Второй — `gpt-6-luna`: почти втрое дешевле, на одно принятое меньше. `gemini-3.8-flash` и `claude-sonnet-5` не лучше по качеству, но в 3 и 10 раз дороже. `claude-sonnet-5` на 50 организациях вышел бы за лимит проверки в 50 ₽.
- **`gpt-4.1-mini` стоит заменить.** 6 из 9, а в отдельном опыте (`instruction_in_comment` × 3) она **дважды из трёх выполнила инструкцию из комментария**. Проверка S5-06 оба раза отклонила ответ (`priority_changed`), но модель, которая поддаётся, — плохое умолчание.
- **Открытые рассуждающие модели (deepseek, glm, qwen) не укладываются в 1000 токенов.** `effort=low` они не соблюдают. `qwen3.6-35b-a3b`, единственная модель с хранением в РФ, которая принимает схему, рассуждает всегда: и с `effort=low`, и с `enabled: false`, а `effort: none` отклоняет с 400. Ответ появился бы при лимите в 3–4 тыс. токенов, но это 1–1,5 ₽ за объяснение и выход за лимит проверки.
- **Часть отклонений — не ошибки моделей, а наши.** У пяти моделей `creditor_not_debtor` отклонён как `new_amount` с числом `-0`: модель вставила в текст идентификатор основания `efrsb-event-0`, а разбор чисел прочитал его хвост как отрицательное число. Так же `30` взялось из кода сигнала `revenue_drop_30`. Идентификаторы в тексте недопустимы (пользователь их читать не должен), но код отклонения вводит в заблуждение. Лечится запретом в инструкции (S5-05) и отдельным кодом в проверке (S5-06), после этого лидеров стоит перемерить (≈ 3 ₽).
- **Словарные проверки двух сценариев слишком узкие.** `gone_quiet` ищет «платёж», а верный ответ говорит «поступлений не зафиксировано». `holes_in_the_package` не знает «отсутствуют сведения». Замечания к `files_disagree` справедливы: ни одна модель не назвала противоречие между файлами, это вопрос к инструкции.
- **Отказ провайдера бывает маршрутом, а не моделью.** Два `refused` у `qwen3.8-flash` — это «All providers have been ignored… MODEL_NOT_SUPPORTED»: polza пыталась отправить запрос через OpenRouter, где провайдеры модели выключены настройками приватности. Видно по `evals/results/<время>-errors.jsonl`.

Весь замер обошёлся примерно в 25–30 ₽: 16,4 ₽ видно в таблице, около 5 ₽ — обрезанные ответы `qwen3.6-35b-a3b`, остальное — прочие обрезанные ответы и отдельные опыты.

**Модели с хранением данных в России** (`sber/gigachat-2`, `yandex/yandexgpt-5-lite`, `yandex/yandexgpt-5.1-pro`) в каталоге помечены как соответствующие 152-ФЗ, но **не поддерживают `response_format`** и стоят дороже (91–1120 ₽ за миллион токенов против 47/189 у `gpt-4.1-mini`). Для них есть `AI_RESPONSE_FORMAT=none`: формат тогда спрашивается словами, а соблюдение схемы проверяет только S5-06 — отклонённый ответ стоит запроса и заменяется объяснением по правилам.

**Связь.** Соединение с polza.ai из сети разработчика A рвётся на TLS-рукопожатии примерно в половине попыток (ошибка через 60 с). Успешный вызов занимает 7–35 с. Один повтор (`AI_MAX_RETRIES=1`) при такой доле отказов закрывает три четверти случаев; на месте, где будет стоять сервер, долю отказов надо измерить заново и, если она такая же, поднять `AI_MAX_RETRIES` до 2–3. Таймаут одного вызова (`AI_TIMEOUT_SECONDS=30`) для `gpt-4.1-mini` тесноват — 60 с ближе к правде.

**Настройки** (`.env`): `AI_PROVIDER=polza`, `AI_API_KEY=<ключ>`, `AI_MODEL=openai/gpt-4.1-mini`, `AI_RESPONSE_FORMAT=json_schema|none`. Без ключа служба с `AI_PROVIDER=polza` не стартует — проверка настроек (`--check`) скажет об этом прямо.

### Лимит расходов — в рублях (S5-03)

Заказчик согласовал **1000 ₽ в месяц** (23.09.2026), и считаем мы теперь именно рубли, а не их оценку по токенам: цена каждого вызова приходит в ответе провайдера (`usage.cost_rub`).

Два лимита, разных по природе:

| Лимит | Где живёт | Что делает |
| --- | --- | --- |
| `AI_RUN_RUB_LIMIT` (50 ₽) | в бюджете проверки | одна проверка не может потратить месяц целиком, каким бы большим ни был пакет |
| `AI_MONTH_RUB_LIMIT` (1000 ₽) | в базе службы, таблица `ai_spend` | переживает перезапуск и общий для всех проверок и пользователей |

Месяц читается **один раз, перед первым вопросом модели**: проверка, начавшаяся в пределах лимита, доводится до конца. Выйти за месяц она может **не больше чем на стоимость одного вызова** (доли рубля): остаток месяца становится лимитом этой проверки, и следующий вызов уже не разрешается. Блокировка вокруг каждого вызова купила бы точность, которая при 1000 ₽ не нужна, и заставила бы один медленный ответ ждать остальных.

**Счётчик считает завершённые проверки.** Потраченное записывается в месяц после прогона: если служба перезапустится на середине или запись не удастся, деньги у провайдера уже потрачены, а в счётчике их не будет. Потеря ограничена лимитом одной проверки. Сбой записи при этом **не отменяет проверку** — отчёт уже собран и оплачен, и отказ ничего не вернул бы; в журнале это видно строкой `ai_spend_not_recorded`. Обратное решение принято для чтения: не знаем остаток — не тратим вовсе.

Если месяц исчерпан, модель **не спрашивается вовсе**: в отчёте — рекомендации по правилам, а в итоге проверки прямо сказано «Лимит расходов на ИИ за месяц исчерпан». Это отличается от «спросили, но не получилось» (`explanations_missing`) и в сводке хранится отдельным признаком.

Провайдер, который не сообщает цену, не считается бесплатным: рубли просто не начисляются, а проверку ограничивают лимиты по запросам, токенам и времени. Деньги складываются в `Decimal` и хранятся текстом — 0,0044424 ₽ за вызов при сложении во float «уплыли» бы.

Месяц — календарный, по UTC: та же граница, что у провайдера в кабинете, и она не зависит от часового пояса оператора.

### Что уходит провайдеру — решение заказчика

С нашей стороны: **ИНН не уходит** (в запросе `counterparty_ref`, и с #45 он замаскирован даже внутри ID фактов), комментарии не уходят, пока `AI_SEND_COMMENTS=false`. Уходят: **название организации**, суммы долга и платежей, даты, показатели, сигналы правил и тексты замечаний. Модель по умолчанию — зарубежная (`openai/*` через агрегатора), то есть эти сведения покидают периметр и Россию. Это решение заказчика, а не наше: если ответ «только российское хранение» — ставим `sber/gigachat-2` и `AI_RESPONSE_FORMAT=none`, если «ничего опознающего» — дополнительно выключаем `include_record_ids` и обсуждаем название организации.

## Что записывать перед подключением реального провайдера

1. Провайдер и модель (`name`, `model`), способ доступа (ключ — только в окружении, как `CHECKO_API_KEY`).
2. Какие поля контекста разрешены заказчиком: ИНН по умолчанию не отправляется (`counterparty_ref`, и с #45 маскируется внутри ID фактов и записей), комментарии — только при явном согласии (`include_comments`); `include_record_ids` — ОГРН и GUID сообщений опознают организацию не хуже ИНН, при запрете «ничего опознающего» выключить и их. Сохранённый сырой ответ модели (S5-02) может цитировать комментарии — он живёт в хранилище проверки и удаляется с ней (S6-02), в журналы не попадает. Пробел с ИНН внутри ID фактов закрыт в #45: ID маскируются той же ссылкой, тест `test_request_body_does_not_contain_the_inn_anywhere` проходит.
3. Лимит расходов на проверку и на день (S5-03) и как он считается из `input_tokens`/`output_tokens`.
4. Клиент добавляется в `infrastructure/llm/<provider>.py`, реализует протокол, отображает ошибки транспорта на коды `AiUnavailable`, и регистрируется в `runtime/ai.py` новым значением `AI_PROVIDER`.
