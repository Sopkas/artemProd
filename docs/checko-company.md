# Checko: первый реальный адаптер — S1-05

Реализован `CheckoCompanyDataProvider`: интерфейс совместим с демопровайдером и карточкой S1-03. Адаптер делает один запрос организации; ЕФРСБ и финансы возвращают `unavailable / not_implemented`, а не пустой успешный результат. Автоматической замены реальных данных демоданными нет.

## Запуск

В локальном `.env` или окружении:

```dotenv
DATA_PROVIDER=checko
CHECKO_API_KEY=ваш_ключ
```

Затем запустить `python -m claims_assistant` по README. `TELEGRAM_BOT_TOKEN` и список доступа по-прежнему обязательны. По умолчанию `DATA_PROVIDER=demo`; наличие ключа само по себе реальный режим не включает. Для возврата к демо указать `DATA_PROVIDER=demo`. Перед запуском остановить прежний polling-процесс своего бота.

Проверка ключа происходит при запросе ИНН, не при запуске. Условия тарифа и списания контролируются в кабинете Checko: даже тестовый запрос может учитываться в квоте. Реальные ключи в тестах и CI не используются.

## Подтверждённая схема и отображение

18.09.2026 проверены реальные ответы `POST https://api.checko.ru/v2/company`. Имена и типы полей подтверждены ответами API; официальный URL документации `/integration/api/company` в этом окружении вернул HTTP 403. В тестах используются синтетические значения с такой же минимальной структурой, не сохранённые ответы реальных компаний.

| Поле Checko | Наш результат |
| --- | --- |
| `meta.status` | `ok` допускает разбор; `error` даёт безопасную ошибку; неизвестная форма — `invalid_response` |
| `data.ИНН` | Должен точно совпасть со строкой запрошенного ИНН |
| `data.ОГРН` | 13 цифр, ID записи-источника; URL карточки не придумывается |
| `data.НаимСокр`, иначе `data.НаимПолн` | Факт названия, непустая строка не длиннее 1000 символов |
| `data.ДатаВып` | Дата выписки для `observed_on`; не дата обновления источника и не момент запроса |
| `data.Статус` = `Код: 001`, `Наим: Действует` | Подтверждённая точная пара → `CompanyStatus.ACTIVE` |
| Любой другой код/название статуса | Неизвестное значение с причиной; никогда автоматически не превращается в «действует» или «ликвидирована» |

В реальном ответе также подтверждена пара `000 / Не действует`. Это недостаточно для вывода «ликвидирована»: возможные причины прекращения деятельности нужно нормализовать отдельно. Статусы ликвидации, реорганизации и банкротства пока не сопоставлены. Общие типы в этом PR не меняются; расширение статусов следует согласовать отдельно.

Организация всегда `coverage=partial`: получены только название и ограниченный статус на дату выписки, риски не оценивались. `fetched_at` — время обращения в UTC, `source_updated_at=None`. Пустой/повреждённый ответ, другой ИНН, отсутствие даты или ОГРН не выдаются за отсутствие организации либо отсутствие риска.

## Ошибки и ресурсы

- HTTP 401/403 → `unauthorized`, но 403 с «лимит» в `meta.message` (исчерпан суточный лимит) → `rate_limited / daily_limit`; 429 → `rate_limited`, прочие неуспешные HTTP → `unavailable`. HTTP 404 не означает, что должник не существует.
- Ошибка API внутри HTTP 200 → `unavailable / api_error`; сообщение сервера не пересылается пользователю и не разбирается по ненадёжным текстовым подстрокам.
- Таймаут/сетевой сбой → безопасная ошибка, некорректный JSON/схема → `invalid_response`. Отмена и программные ошибки не поглощаются.
- Один запрос, без повторов и пагинации; положительные лимиты `max_requests`/`max_pages` соблюдаются. Общий таймаут адаптера берётся из `RequestLimits` (20 секунд по умолчанию).
- HTTPS, ключ в JSON-теле POST, переходы по редиректам запрещены. Не используются глобальные настройки прокси из окружения; отдельная настройка маршрута — задача развёртывания.
- Ответ ограничен 2 МиБ. Сессия и ответ закрываются контекстными менеджерами, включая сбой и отмену. Тексты исключений и полный ответ не журналируются; formatter скрывает оба ключа.
- Используется уже закреплённый `aiohttp==3.14.3`, теперь явно указанный прямой зависимостью пакета.

## S3-04: ЕФРСБ и финансы (схемы подтверждены 20.09.2026)

Разделы ЕФРСБ и финансов реализованы поверх S1-05. Каждый раздел падает независимо в результат раздела, а не в исключение; отмена и программные ошибки пробрасываются. Ключ только в теле POST, ответ ограничен 2 МиБ, редиректы и прокси из окружения запрещены — как в организации.

**Схемы сверены с реальными ответами** (20.09.2026, временный ключ разработчика, бесплатный тариф; перечень проверенного — в [интеграциях](integrations.md)). Финансы совпали с предположением полностью. В записях ЕФРСБ предполагаемого поля `Номер` нет: запись опознаётся по `GUID`, ссылка на «Федресурс» приходит в `URL`, русское название типа — в `ТипНаим`, машинный код — в `Тип`. Разбор исправлен по реальным полям. Реальные ответы в репозитории не хранятся: примеры в `tests/fixtures/checko/*_live_shape.json` повторяют форму, но со синтетическими значениями.

### ЕФРСБ — `POST /v2/bankruptcy-messages`

- Тело `{"key","inn","page"}`. Пагинация до `min(СтрВсего, max_pages, max_requests)` страниц; повторов нет.
- Запись: `{"GUID","URL","Дата","Тип","ТипНаим","НомерДела","Суд","РешенСуда"}`. Каждая запись → факт `BANKRUPTCY_EVENT` с датой и `Evidence` (источник, `GUID` как идентификатор записи, ссылка на «Федресурс»; сохраняется только ссылка на `https://`). Значение факта — `ТипНаим` плюс номер дела («Сведения о судебном акте, дело А00-0000/2025»); машинный код `Тип` пользователю не показывается. Запись без распознанной даты пропускается и отмечается в `missing`; при отсутствии `GUID` берётся `Номер`, затем суррогат `инн:индекс`.
- **Типы событий классифицирует `domain/efrsb`**, адаптер только применяет: сообщение по открытому делу → `BANKRUPTCY_EVENT`, по прекращённому → `BANKRUPTCY_CLOSED` (история, пометка «Есть сообщения о прекращённых делах»). Подтверждённая процедура из сообщения не выводится: реестр отвечает по ИНН без роли, поэтому при сообщениях по открытым делам coverage `partial` с пометкой «Роль организации в деле о банкротстве не подтверждена…» (S3-06). Неполная выборка (страниц больше бюджета) → `partial` с явной причиной. **Сбой на странице 2 и дальше** (таймаут, сеть, HTTP-ошибка, лимит, битый ответ) полученные сообщения не выбрасывает: раздел `partial` с пометкой «Выборка сообщений ЕФРСБ неполная; проверьте реестр вручную», а сам сбой (`code`, текст) лежит в `ExternalSnapshot.interrupted` — ответ не окончательный, конвейер может его не сохранять и спросить источник при повторе. Обрезка по бюджету страниц — наш выбор, `interrupted` не ставит. `unavailable` — только при сбое на первой странице. Ноль записей при полной выборке → `complete` без фактов.

### Финансы — `POST /v2/finances`

- Тело `{"key","inn"}`. Схема: `data` по годам (`"2023": {"2110": выручка, "2400": чистая прибыль}}`), коды строк ОКУД; рядом приходят блоки `company` и `bo.nalog.ru`, они не читаются. Пустой `data` у существующей организации — нормальный ответ «отчётности нет».
- Проецируются два последних **последовательных** года **с данными** как факты `REVENUE`/`NET_PROFIT` с периодом года и единицей `RUB`; суммы — точный `Decimal` (float через строку). Год с данными — тот, где есть хотя бы одна из строк 2110/2400: пустая форма или баланс без выручки в пару не идут. Нет двух последовательных лет → `partial` с причиной. Последний год с данными не вошёл в пару (есть 2025, нет 2024) → `partial` «Последний год отчётности (2025) без предыдущего; динамика — по 2022–2023». Строка есть только за один год пары → `partial` «Нет строки 2110 (выручка) за 2024». Год позже последнего с данными пришёл без обеих строк → `partial` «Отчётность за 2024 без строк 2110 и 2400; динамика — по 2022–2023» (пустые годы раньше данных не упоминаются); пусто → `partial / недоступна`. Коэффициенты (рост, падение выручки) считает скоринг S3-05, не адаптер.

### Ошибки

HTTP 401/403 → `unauthorized`, 429 → `rate_limited`, прочие → `http_error/unavailable`; **403 с «лимит» в `meta.message` → `rate_limited / daily_limit`** (так Checko отвечает на исчерпанный суточный лимит, проверено 27.09.2026: `"Превышен суточный лимит запросов для бесплатного тарифа"`, отклонённые запросы в счётчик не идут), у 403 для этого тело дочитывается с тем же пределом 2 МиБ, нечитаемое тело — обычный `unauthorized`; `meta.status=error` → `unavailable / api_error`; **пустой `data` при `status=ok` и сообщении «не найдено» → `not_found`** (организации нет в источнике — это ответ, а не поломка); кривой JSON/схема → `invalid_response`; таймаут/сеть → безопасная ошибка. Тексты исключений и полный ответ не журналируются; ключ не попадает в результат.

Ключ с доступом ко всем трём разделам проверен 20.09.2026 (бесплатный тариф). Не проверено: предел запросов тарифа и поведение при исчерпании квоты.

## S3-06: контрактные примеры и трактовка событий

Синтетические примеры ответов лежат в `tests/fixtures/checko/`, сценарии — `tests/unit/test_checko_contract.py`. Главный инвариант: неожиданный ответ никогда не превращается в «полная проверка, риска нет».

| Сценарий | Организация | ЕФРСБ | Финансы |
| --- | --- | --- | --- |
| Организация не найдена | `not_found` во всех трёх разделах: пустой `data` при `status=ok` и сообщении источника «Не найдено ни одной организации…» | то же | то же |
| Пустые данные без такого сообщения | `invalid_response` (сломанный ответ, а не «организации нет») | `complete` без фактов — и при `СтрВсего: 1`, и при самосогласованных нуле страниц (`ЗапВсего: 0`, пустые `Записи`) | `partial / недоступна` — отчётности нет |
| Неизвестное событие | — | факт сохраняется с исходным названием, `partial` + «требует проверки» | — |
| Исчерпанная квота | `meta.status=error` в HTTP 200 → `api_error`; HTTP 429 → `rate_limited`; суточный лимит бесплатного ключа — HTTP 403 → `rate_limited / daily_limit`; текст сервера не пересылается; в адаптере без повторов | то же | то же |
| Таймаут | безопасная ошибка `timeout`, ключ не журналируется | то же | то же |
| Изменение структуры | переименованные поля → `invalid_response` | переименованный конверт → `invalid_response`; переименованные поля записи → запись не учтена и это явно указано | нет годов/кодов строк → `partial` без фактов |

Формы реальных ответов (20.09.2026) зафиксированы в примерах `company_not_found`, `efrsb_not_found`, `finances_not_found`, `efrsb_live_shape`, `finances_live_shape`: поля и конверт настоящие, значения синтетические. Сами ответы источника в репозитории не хранятся. Расхождения с источником правятся только в `bankruptcy.py` / `finances.py` / `company_data.py`.

### Вопросы специалисту по трактовке событий ЕФРСБ

До ответов каждое сообщение — `unresolved_bankruptcy_event` (высокий, «требует проверки»), `confirmed_procedure` не выводится.

1. Какие типы сообщений означают введённую процедуру (наблюдение, финансовое оздоровление, внешнее управление, конкурсное производство, реструктуризация долгов) и должны давать «критичный»?
2. Уведомление кредитора о намерении обратиться с заявлением — «высокий» с проверкой или ниже?
3. Какие события отменяют или завершают процедуру (прекращение производства, отказ во введении, завершение) и насколько далеко назад смотреть?
4. Сообщения, где контрагент участвует не как должник (кредитор, арбитражный управляющий), — исключать?
5. Сколько лет сообщение остаётся значимым, если нет последующих событий?
