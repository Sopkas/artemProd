# Checko: первый реальный адаптер — S1-05

Реализован `CheckoCompanyDataProvider`: интерфейс совместим с демопровайдером и карточкой S1-03. Адаптер делает один запрос организации; ЕФРСБ и финансы возвращают `unavailable / not_implemented`, а не пустой успешный результат. Автоматической замены реальных данных демоданными нет.

## Запуск

В локальном `.env` или окружении:

```dotenv
DATA_PROVIDER=checko
CHECKO_API_KEY=ваш_ключ
```

Затем запустить `python -m claims_assistant` по README. `TELEGRAM_BOT_TOKEN` и список доступа по-прежнему обязательны. По умолчанию `DATA_PROVIDER=demo`; наличие ключа само по себе реальный режим не включает. Для возврата к демо указать `DATA_PROVIDER=demo`. Перед запуском остановить прежний polling-процесс своего бота.

Проверка ключа происходит при запросе ИНН, не при запуске. Условия тарифа и списания контролируются в кабинете Checko: даже тестовый запрос может учитываться в квоте. Реальные ключи в тестах и CI не используются.

## Подтверждённая схема и отображение

18.09.2026 проверены реальные ответы `POST https://api.checko.ru/v2/company`. Имена и типы полей подтверждены ответами API; официальный URL документации `/integration/api/company` в этом окружении вернул HTTP 403. В тестах используются синтетические значения с такой же минимальной структурой, не сохранённые ответы реальных компаний.

| Поле Checko | Наш результат |
| --- | --- |
| `meta.status` | `ok` допускает разбор; `error` даёт безопасную ошибку; неизвестная форма — `invalid_response` |
| `data.ИНН` | Должен точно совпасть со строкой запрошенного ИНН |
| `data.ОГРН` | 13 цифр, ID записи-источника; URL карточки не придумывается |
| `data.НаимСокр`, иначе `data.НаимПолн` | Факт названия, непустая строка не длиннее 1000 символов |
| `data.ДатаВып` | Дата выписки для `observed_on`; не дата обновления источника и не момент запроса |
| `data.Статус` = `Код: 001`, `Наим: Действует` | Подтверждённая точная пара → `CompanyStatus.ACTIVE` |
| Любой другой код/название статуса | Неизвестное значение с причиной; никогда автоматически не превращается в «действует» или «ликвидирована» |

В реальном ответе также подтверждена пара `000 / Не действует`. Это недостаточно для вывода «ликвидирована»: возможные причины прекращения деятельности нужно нормализовать отдельно. Статусы ликвидации, реорганизации и банкротства пока не сопоставлены. Общие типы в этом PR не меняются; расширение статусов следует согласовать отдельно.

Организация всегда `coverage=partial`: получены только название и ограниченный статус на дату выписки, риски не оценивались. `fetched_at` — время обращения в UTC, `source_updated_at=None`. Пустой/повреждённый ответ, другой ИНН, отсутствие даты или ОГРН не выдаются за отсутствие организации либо отсутствие риска.

## Ошибки и ресурсы

- HTTP 401/403 → `unauthorized`, 429 → `rate_limited`, прочие неуспешные HTTP → `unavailable`. HTTP 404 не означает, что должник не существует.
- Ошибка API внутри HTTP 200 → `unavailable / api_error`; сообщение сервера не пересылается пользователю и не разбирается по ненадёжным текстовым подстрокам.
- Таймаут/сетевой сбой → безопасная ошибка, некорректный JSON/схема → `invalid_response`. Отмена и программные ошибки не поглощаются.
- Один запрос, без повторов и пагинации; положительные лимиты `max_requests`/`max_pages` соблюдаются. Общий таймаут адаптера берётся из `RequestLimits` (20 секунд по умолчанию).
- HTTPS, ключ в JSON-теле POST, переходы по редиректам запрещены. Не используются глобальные настройки прокси из окружения; отдельная настройка маршрута — задача развёртывания.
- Ответ ограничен 2 МиБ. Сессия и ответ закрываются контекстными менеджерами, включая сбой и отмену. Тексты исключений и полный ответ не журналируются; formatter скрывает оба ключа.
- Используется уже закреплённый `aiohttp==3.14.3`, теперь явно указанный прямой зависимостью пакета.

## S3-04: ЕФРСБ и финансы (предполагаемые схемы)

Разделы ЕФРСБ и финансов реализованы поверх S1-05. Каждый раздел падает независимо в результат раздела, а не в исключение; отмена и программные ошибки пробрасываются. Ключ только в теле POST, ответ ограничен 2 МиБ, редиректы и прокси из окружения запрещены — как в организации.

**Важно про схемы.** Подтверждён только конверт пагинации ЕФРСБ (`ЗапВсего`, `СтрВсего`, `СтрТекущ`, `Записи`). Поля отдельной записи и вся схема финансов — **обоснованное предположение**, изолированное в `infrastructure/checko/bankruptcy.py` и `finances.py`; сверка с реальным ответом — правка только там. Тесты используют синтетические ответы такой же минимальной формы, реальные ответы не сохранялись.

### ЕФРСБ — `POST /v2/bankruptcy-messages`

- Тело `{"key","inn","page"}`. Пагинация до `min(СтрВсего, max_pages, max_requests)` страниц; повторов нет.
- Предполагаемая запись: `{"Дата":"ГГГГ-ММ-ДД","Тип":str,"Номер":str}`. Каждая запись → факт `BANKRUPTCY_EVENT` с датой и `Evidence` (источник + `Номер` либо `инн:индекс`). Запись без распознанной даты пропускается и отмечается в `missing`.
- **Типы событий не классифицируются**: по `scoring.md` неподтверждённый тип требует ручной проверки, поэтому подтверждённая процедура из текста не выводится. При наличии записей coverage `partial` с пометкой «значение требует проверки специалистом». Неполная выборка (страниц больше бюджета) → `partial` с явной причиной. Ноль записей при полной выборке → `complete` без фактов.

### Финансы — `POST /v2/finances`

- Тело `{"key","inn"}`. Предполагаемая схема: `data` по годам (`"2023": {"2110": выручка, "2400": чистая прибыль}}`), коды строк ОКУД.
- Проецируются два последних **последовательных** года как факты `REVENUE`/`NET_PROFIT` с периодом года и единицей `RUB`; суммы — точный `Decimal` (float через строку). Нет двух последовательных лет → `partial` с причиной; пусто → `partial / недоступна`. Коэффициенты (рост, падение выручки) считает скоринг S3-05, не адаптер.

### Ошибки

HTTP 401/403 → `unauthorized`, 429 → `rate_limited`, прочие → `http_error/unavailable`; `meta.status=error` → `unavailable / api_error`; кривой JSON/схема → `invalid_response`; таймаут/сеть → безопасная ошибка. Тексты исключений и полный ответ не журналируются; ключ не попадает в результат.

Реальная интеграция не объявляется готовой без ключа с доступом к разделам: без него код и тесты работают на синтетических фактах.
