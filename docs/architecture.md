# Архитектура MVP

Статус: проект решений, код ещё не реализован. Основной сценарий — ограниченный конвейер анализа одной загрузки. Автономный агент, выбирающий действия и инструменты, здесь не нужен.

## Границы модулей

| Модуль | Отвечает за | Не должен содержать |
| --- | --- | --- |
| `presentation/telegram` | Состояние диалога, загрузку файлов, команды, отображение результата | Расчёт показателей и HTTP-запросы Checko |
| `application` | Импорт пакета, запуск проверки, получение статуса и отчёта; интерфейсы адаптеров | Зависимость от aiogram и формата ответа Checko |
| `domain` | Сущности, расчёты, проверяемые сигналы, приоритет | Сеть, БД, Telegram, вызовы ИИ |
| `infrastructure` | Реализацию внешних клиентов, Excel, хранения | Решение об итоговом приоритете |
| `runtime` | Конфигурацию, связывание зависимостей, запуск бота и обработчика | Новые бизнес-правила |

Направление зависимостей: `presentation → application → domain`; `infrastructure` реализует интерфейсы из `application` и использует типы `domain`. `runtime` собирает всё вместе. Интерфейсы добавляются для реальных границ: провайдер данных, ИИ, хранилище, читатель таблиц, генератор отчёта.

## Обработка задания

1. Создать `AnalysisRun` с владельцем и фиксированной датой анализа.
2. Сохранить файлы, типы загрузок, контрольные суммы и ошибки строк. Повтор одного файла внутри пакета не дублирует данные.
3. При запуске зафиксировать входной пакет; новые файлы потребуют новой проверки.
4. Сохранить отдельное задание на каждый уникальный ИНН.
5. Получить и нормализовать внешние сведения; сохранить результаты каждого источника, включая ошибки.
6. Рассчитать показатели и сигналы; сохранить версии правил и основания.
7. Получить и проверить ИИ-объяснение либо применить шаблон.
8. Создать итоговый файл, сохранить ссылку на артефакт, отправить пользователю результат.

Состояния проверки: `draft → queued → running → completed | partial | failed`. Некорректные строки, сбои источников или шаблон вместо ИИ дают `partial`, если полезный отчёт сформирован. `failed` означает отсутствие пригодного результата. Неполнота загруженных данных отдельно отражается в покрытии анализа.

Один фоновый обработчик берёт задания из SQLite. Сетевые операции не выполняются внутри транзакции БД. Чтение и запись больших файлов выносятся из цикла обработки Telegram-сообщений. На старте приложение восстанавливает прерванные задания по сохранённым шагам.

Результат шага сохраняется по ключу `(run_id, inn, step, version)`. Сбой после получения ответа, но до сохранения может привести к повторному платному запросу — гарантии «ровно один вызов» нет. Завершённые сохранённые шаги повторно не выполняются. Состояние доставки отчёта хранится отдельно от результата анализа; повторная выдача готового отчёта не запускает проверку заново.

## Минимальная модель данных

| Сущность | Основные данные |
| --- | --- |
| `User` | Разрешённый Telegram ID |
| `AnalysisRun` | Владелец, дата анализа, статус, прогресс, режим demo/live, версии, лимиты |
| `UploadedFile` | Проверка, тип, контрольная сумма, путь, ошибки, период покрытия |
| `Counterparty` | ИНН, название; идентичность по ИНН |
| `DebtSnapshot` | Проверка, ИНН, дата, долг, дни просрочки, последний платёж |
| `Payment` | Проверка, ИНН, ID платежа, дата, сумма, ссылка на строку |
| `Interaction` | Проверка, ИНН, ID записи, дата, канал, комментарий |
| `ExternalSnapshot` | ИНН, источник, дата получения, статус, полнота, нормализованные факты |
| `RiskAssessment` | Проверка, ИНН, показатели, сигналы с основаниями, приоритет, покрытие |
| `Recommendation` | Проверка, ИНН, текст, ссылки на факты, версия модели/инструкции, статус проверки |
| `ReportArtifact` | Проверка, путь, дата формирования, статус доставки |

Все внутренние данные принадлежат конкретной проверке и владельцу; поиск только по ИНН не должен смешивать долги разных пользователей. Деньги — `Decimal` в расчётах и целое число копеек в БД. Даты хозяйственных событий — календарные даты; технические временные отметки — UTC.

## Контракты интеграций

| Операция | Вход | Выход | Эффект |
| --- | --- | --- | --- |
| `CompanyDataProvider.fetch` | ИНН, перечень разделов, лимиты | Снимки источников и ошибки | Чтение внешнего API, возможный расход квоты |
| `RecommendationProvider.explain` | Факты, приоритет, комментарии, лимит ответа | Структурированное объяснение | Запрос ИИ, возможный расход бюджета |
| `AnalysisRepository` | Владелец, ID проверки, результат шага | Сохранённое состояние | Запись в локальную БД |
| `ReportWriter.build` | Готовые оценки и происхождение фактов | Локальный `.xlsx` | Создание отчёта |

Это интерфейсы приложения, они не передаются модели как доступные инструменты. Загрузку, запросы, расчёты и выдачу выполняет код в фиксированном порядке.

## ИИ и контекст

Один ограниченный запрос на контрагента. Модель получает готовые показатели, выбранные внешние события, приоритет и последние комментарии с ID записей. Полная таблица, ключи, телефоны и контактные ФИО не нужны для этой задачи и в контекст не включаются.

Порядок контекста: постоянная инструкция → схема ответа → факты конкретной проверки → комментарии как недоверенный текст. Обещание клиента обозначается как обещание со ссылкой на запись, а не как установленный платёж. Инструкции внутри комментариев и текстов внешнего источника не исполняются.

Схема ответа: `summary`, `interaction_findings[]`, `suggested_actions[]`, `evidence_ids[]`, `limitations[]`. Для каждого утверждения нужен ID переданного факта. Валидатор проверяет структуру, существование ссылок, отсутствие новых сумм, дат и изменения приоритета. Такие проверки не доказывают смысловую корректность текста — она отдельно оценивается на примерах.

При слишком большом контексте сохраняются все критичные структурированные сигналы и последние комментарии в пределах лимита; пропуски обозначаются в отчёте. Между контрагентами история диалога не переносится. Состояние задания хранится в БД, поэтому отдельная память агента и автоматическое сжатие диалога в MVP не требуются.

## Ограничения и восстановление

Начальные инженерные настройки, которые проверяются на пилоте:

- До 50 ИНН, до 10 МБ на файл, до 10 000 строк на пакет; также ограничить размер распакованного `.xlsx`.
- Таймаут внешнего запроса — 20 секунд; до двух повторов временных ошибок с увеличением паузы и учётом `Retry-After`.
- Для ИИ — один основной вызов и максимум один повтор; при неудаче использовать шаблон. Начальный лимит ответа — 1 000 токенов, входа — 6 000 токенов.
- До 20 страниц событий на ИНН; при достижении лимита пометка о неполной выборке обязательна.
- До 15 минут на проверку и до 1 500 попыток внешних HTTP-запросов суммарно, включая страницы и повторы. Эти потолки не заменяют отдельный денежный лимит, рассчитываемый по тарифам выбранных провайдеров.
- При исчерпании квоты, денег или времени сохранить готовую часть, обозначить непроверенных контрагентов и завершить задание со статусом `partial`.

Внешние результаты кэшируются по ИНН, источнику и параметрам при допустимости по условиям поставщика. Для пилота целевой срок кэша — один час; это настройка, не обещание актуальности реестра. Дата получения и дата самого события показываются отдельно.

## Доступ, хранение, диагностика

Доступ к файлам и отчётам проверяется по владельцу при каждом действии. Реальные данные используются после согласования допустимых каналов Telegram и ИИ с заказчиком. ИИ можно отключить настройкой; демонстрации готовятся на синтетических данных.

Ключи находятся в переменных окружения. Логи содержат ID проверки, этап, длительность, код результата, повторы и потребление API/ИИ; не содержат исходные файлы, комментарии, токены и URL с ключом. Рабочее хранилище находится вне репозитория, срок хранения задаётся конфигурацией, очистка удаляет файлы и связанные данные проверки.

Приложение готовит рекомендации и отчёт для владельца проверки. В MVP нет отправки сообщений должникам, изменения 1С и выполнения юридических действий.

## Проверка качества

Модульные проверки покрывают расчёты и приоритет; интеграционные — файлы, нормализацию ответов, сохранение и восстановление задания. Приёмочные проверки проходят весь путь от файла до отчёта. В `evals/` хранятся примеры для ИИ: выдуманные факты, неверные ссылки, противоречивые комментарии и попытки изменить инструкции.

Для каждого отчёта фиксируются версия правил, версия инструкции и модель. Метрики пилота: время ручной и автоматической проверки одного и того же списка, доля неполных проверок, стоимость отчёта и оценка полезности специалистом.
