# Эксплуатация: хранение, копии, восстановление, обновление — S6-02

Состояние: 19.09.2026, реализовано и проверено локально (Windows). Размещение на сервере и systemd — S6-01.

## Срок хранения и очистка

Данные должников принадлежат заказчику и не должны храниться дольше согласованного срока. Срок задаётся настройкой, очистка встроена в бота и есть как команда.

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| `RETENTION_DAYS` | `30` | Проверка старше этого срока (по последнему изменению) удаляется вместе с загруженными файлами, отчётом и результатами шагов |
| `RETENTION_SWEEP_SECONDS` | `21600` (6 ч) | Как часто бот делает проход; первый проход — при старте |

Правила (`application/retention.py`, `purge_expired`):

- Удаляются проверки в состояниях `draft` (черновик, который так и не запустили), `completed`, `partial`, `failed`. **`queued` и `running` не трогаются никогда.**
- Сначала удаляется каталог файлов проверки (`<STORAGE_PATH>/<run_id>/`), затем записи в БД. Если файлы удалить не удалось, записи остаются — следующий проход повторит; в логе `purge_files_failed run_id=…`.
- Проверка, которая ожила между выборкой и удалением (черновик запустили, `failed` перезапустили), не удаляется: перед удалением файлов состояние перечитывается, а удаление записей несёт то же условие «истекла на момент выборки».
- Проход идемпотентен; в логе `retention_sweep expired=N removed=N failed=N`.
- Ручной запуск: `python -m claims_assistant.ops purge` (`--dry-run` — только посчитать). Команда читает те же настройки из `.env`.

Срок 30 дней — стартовое значение для пилота; согласовать с заказчиком до реальных данных и записать в карточку S6-02.

## Резервное копирование

`python -m claims_assistant.ops backup` — снимок в `<BACKUP_PATH>/<UTC-время>/`:

```
data/backups/20260919T160035Z/
  claims.sqlite3   — копия БД через SQLite online backup API (консистентна при работающем боте)
  uploads/         — копия каталога загрузок и отчётов
  manifest.json    — время, число проверок и файлов
```

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| `BACKUP_PATH` | `data/backups` | Куда класть снимки (лучше — другой диск или примонтированное хранилище) |
| `BACKUP_KEEP` | `7` | Сколько новейших снимков хранить; старые удаляются при создании нового |

- Копию можно снимать **при работающем боте**: БД копируется через `sqlite3.Connection.backup()`, а не копированием файла. Каталог загрузок копируется как есть; файл, дописываемый в момент копии (редко — загрузка идёт секунды), попадёт в следующую копию.
- Для сервера (S6-01): `cron`/`systemd timer` раз в сутки, снимки — на отдельный диск или в объектное хранилище; каталог копий хранит те же данные должников — те же права доступа и тот же срок хранения, что у рабочих данных.
- **Копии продлевают срок хранения.** Ротация идёт по числу снимков, а не по возрасту: проверка, удалённая очисткой, живёт в снимках ещё `BACKUP_KEEP` × интервал копий. При ежедневных копиях и значениях по умолчанию фактический срок хранения данных должника — `RETENTION_DAYS` + `BACKUP_KEEP` дней = до 37 дней. Согласовывать с заказчиком именно эту сумму; если нужен жёсткий срок — уменьшить `BACKUP_KEEP` или удалять старые снимки по возрасту отдельным заданием.
- Если копия снята одновременно с проходом очистки, `verify` может показать `отсутствует файлов > 0` (база скопирована до удаления, каталог — после). В этом случае просто снять копию ещё раз.
- `python -m claims_assistant.ops list` — список снимков.

## Проверка и восстановление

`python -m claims_assistant.ops verify <снимок>` — открывает копию: `PRAGMA integrity_check`, число проверок и файлов, и что **каждый** файл, записанный в БД (загрузки и отчёты), есть в `uploads/` снимка. Код возврата `0` только при полном совпадении. Проверять каждую копию, на которую рассчитываете.

Восстановление — **только при остановленном боте** (иначе SQLite продолжит писать в подменённый файл):

1. Остановить бота (локально — `Stop-Process` по `logs/telegram.pid`; на сервере — `systemctl stop`).
2. `python -m claims_assistant.ops restore <снимок> --yes`. Команда сначала проверяет копию, затем откладывает текущие БД **вместе с её служебными файлами SQLite** (`-journal`, `-wal`, `-shm` — «горячий» журнал после сбоя иначе был бы применён к восстановленной копии) и загрузки как `claims.sqlite3.before-restore-<UTC-время>` и `uploads.before-restore-<UTC-время>`, и копирует снимок на их место. Отложенное никогда не удаляется автоматически — повторное восстановление другого снимка не уничтожит то, что отложило первое. Без `--yes` команда только объясняет и ничего не делает.
3. Запустить бота: при старте он применит миграции, если выпуск ушёл вперёд снимка.
4. Убедиться, что `/status` и «Отчёт» отдают ожидаемое; после этого `*.before-restore-*` можно удалить вручную.

**Проверено 19.09.2026 на копии рабочих данных разработчика** (Windows, бот работал): снимок с 3 проверками и 4 файлами → `verify` ok, 0 отсутствующих → `restore` в отдельный каталог → репозиторий открылся, 3 проверки, все загрузки и оба отчёта читаются. Автотесты: `tests/unit/test_backup.py` (копия при открытом и пишущем репозитории, ротация, отсутствующие файлы и битая копия, восстановление после потери БД и файла, отказ восстанавливать битую копию, команды `ops`), `tests/unit/test_retention.py` (memory и SQLite).

## Обновление выпуска

1. `python -m claims_assistant.ops backup` — снимок до обновления.
2. Остановить бота.
3. `git fetch && git checkout <тег или main>`; `pip install -r requirements.txt` и `pip install --no-build-isolation --no-deps -e .`; `pip check`.
4. Сверить `.env` с `README` (новые настройки имеют значения по умолчанию; обновление их не требует).
5. Запустить бота: миграции применяются автоматически при старте (`alembic upgrade head` внутри `open_sqlite_repository`); в логе — `storage_ready`, затем `bot_started`. Если старт упал на миграции — бот не начнёт обслуживать пользователей; см. откат.
6. Ручная проверка: `/start`, «Статус», «Отчёт» по последней проверке.

## Возврат к предыдущему выпуску

Порядок зависит от того, менялась ли схема БД между выпусками (`src/claims_assistant/infrastructure/persistence/migrations/versions/`).

- **Схема не менялась:** остановить бота → `git checkout <предыдущий тег>` → переустановить пакет → запустить. Данные совместимы.
- **Схема менялась и у миграции есть `downgrade`:** остановить бота → на новом коде `alembic downgrade <ревизия предыдущего выпуска>` (из корня репозитория, `alembic.ini` там) → `git checkout <предыдущий тег>` → переустановить → запустить. Проверки, созданные новым выпуском, могут потерять поля, которых не было в старой схеме, — это ожидаемо.
- **Понижение невозможно или сомнительно:** остановить бота → `git checkout <предыдущий тег>` → `python -m claims_assistant.ops restore <снимок, снятый перед обновлением> --yes` → запустить. Проверки, сделанные после снимка, теряются — пользователям сказать об этом явно.

В любом случае перед откатом — свежий `backup`, чтобы можно было вернуться и вперёд.

## Что записывать

- В `.env` — реальные `RETENTION_DAYS` и `BACKUP_PATH` после согласования с заказчиком.
- В карточку S6-02 — дату последней проверки восстановления и на каком снимке; повторять после каждого изменения схемы.
