# Приёмочные сценарии — S6-03

Четыре сценария из roadmap S6-03: полный путь двух пользователей, отказ в доступе к чужим отчётам, остановка во время анализа, повторная доставка. Каждый есть в двух видах: **автоматический** (`tests/e2e/test_two_users.py` — настоящий стек: SQLite, файлы, диалог, обработчик с полным конвейером, уведомления; подменены только транспорт Telegram, внешний источник и модель) и **ручной** — для двух живых аккаунтов Telegram (Сергей `1179483382` и Андрей `765226279`, оба в `ALLOWED_TELEGRAM_IDS`). Результат ручного прогона записывать в карточку S6-03 датой и кто проходил.

## Перед ручным прогоном

Бот запущен один (`logs/telegram.pid` или `systemctl status`). У того, кто его держит, есть журнал и возможность остановить процесс. В `.env`:

```
DATA_PROVIDER=demo
DEMO_SCENARIO=ordinary
DEMO_PACKAGE=false
AI_PROVIDER=off
RUN_REQUEST_LIMIT=30000
```

- `DEMO_SCENARIO=ordinary` — приоритеты в таблице выше посчитаны для него; с `alarm` у всех будет «Высокий».
- `RUN_REQUEST_LIMIT=30000` нужен только сценарию 3 (см. там), остальным не мешает.
- База лучше пустая или отдельная (`DATABASE_PATH`), чтобы старые проверки не мешали.

**Прогон только в демо-режиме.** Признак: на листе «О проверке» в строке «Режим» стоит «ДЕМО — синтетические данные», а не «Реальные данные», и пояснения начинаются с «По правилам:». На живом источнике (`DATA_PROVIDER=checko`):

- каждая организация тратит 3 запроса Checko из 100 в сутки, а источник отвечает «Организация с таким ИНН не найдена» — ИНН вымышленные;
- полнота у всех «неполная», и организации с ожидаемым «Низкий» получают «Недостаточно данных» (проверено 06.10.2026 на пакете Андрея: остальные приоритеты совпали);
- **`ostanovka-kontragenty.xlsx` отправлять нельзя:** суточный лимит кончится на первых 33 организациях из 10 000.

## 1. Два пользователя — полный путь

| Шаг | Ожидание |
| --- | --- |
| Оба, почти одновременно: «Новая проверка» → `01.10.2026` → свой `…-kontragenty.xlsx` | «Пакет принят», организаций: 4, ошибок нет |
| Оба: «Добавить взаимодействия» → свой `…-vzaimodeystviya.xlsx` → «Запустить проверку» | Каждому — «Проверка поставлена в очередь» |
| Ждать | Каждому приходит **своё** уведомление «Проверка завершена…» и **свой** `otchet-….xlsx` |
| Открыть отчёт | На «Приоритетах» только свои четыре ИНН с приоритетами из таблицы выше; на «Хронологии» только свои записи («Запись Андрея…» или «Запись Сергея…») |
| Оба: «Статус», «Отчёт» | Свой статус, свой файл |

Автотест: `test_two_users_each_get_their_own_report` (порядок обработки — по очереди, внешние запросы по каждому ИНН по разу).

## 3. Остановка во время анализа

**В демо-режиме обычную проверку руками не остановить:** 500 организаций считаются за 0,6 с. Поэтому нужен большой файл и поднятый лимит запросов. `ostanovka-kontragenty.xlsx` с `RUN_REQUEST_LIMIT=30000` считается около 13 с (замер на ноутбуке разработчика); со значением по умолчанию `1500` — около 4 с, и после первых 500 организаций остальные получают «лимит исчерпан».

| Шаг | Ожидание |
| --- | --- |
| «Новая проверка» → `01.10.2026` → `ostanovka-kontragenty.xlsx` → «Запустить проверку» | «Проверка поставлена в очередь»; в логе `run_started` |
| Через 3–5 секунд остановить бота (`Stop-Process` / `systemctl stop`) | Уведомления нет; в логе нет `run_finished` |
| Запустить бота снова | В логе `run_recovered`, затем `run_finished`; пользователю приходит уведомление и отчёт **один раз** |
| В логе | Внешние запросы только по организациям, не сохранённым до остановки (`external_fetch` шаги переиспользуются); модель не спрашивается заново по сохранённым ответам |

Если проверка успела закончиться до остановки (`run_finished` уже в логе), повторить с новой проверкой и остановить бота раньше.

Автотест: `test_a_run_interrupted_mid_analysis_is_finished_by_the_next_process` — источник «зависает» на второй организации, задача обработчика убивается, новый процесс на той же БД: `recover` → проверка `completed`, `attempts=2`, внешний запрос только по второй организации.

## 4. Повторная доставка

| Шаг | Ожидание |
| --- | --- |
| «Отчёт» дважды | Тот же файл дважды; новой проверки и новых обращений к источникам/модели нет (`/status` — та же проверка) |
| Сымитировать сбой отправки (например, отключить сеть на секунду и нажать «Отчёт») | «Не удалось отправить файл. Попробуйте ещё раз…»; повтор — файл приходит |

Автотест: `test_report_is_delivered_again_and_a_failed_delivery_is_retried` (`fail_once` транспорта → `failed`-доставка → повтор → `delivered`).
