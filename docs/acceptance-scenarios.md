# Приёмочные сценарии — S6-03

Четыре сценария из roadmap S6-03: полный путь двух пользователей, отказ в доступе к чужим отчётам, остановка во время анализа, повторная доставка. Каждый есть в двух видах: **автоматический** (`tests/e2e/test_two_users.py` — настоящий стек: SQLite, файлы, диалог, обработчик с полным конвейером, уведомления; подменены только транспорт Telegram, внешний источник и модель) и **ручной** — для двух живых аккаунтов Telegram (Сергей `1179483382` и Андрей `765226279`, оба в `ALLOWED_TELEGRAM_IDS`). Результат ручного прогона записывать в карточку S6-03 датой и кто проходил.

Перед ручным прогоном: бот запущен один (`logs/telegram.pid` или `systemctl status`), `DATA_PROVIDER=demo`, `AI_PROVIDER=stub` или `off`.

## 1. Два пользователя — полный путь

| Шаг | Ожидание |
| --- | --- |
| Оба: «Новая проверка» → «Сегодня» → свой шаблон обратно → «Запустить проверку» (можно почти одновременно) | Каждому — «Проверка поставлена в очередь» |
| Ждать | Каждому приходит **своё** уведомление «Проверка завершена…» и **свой** `otchet-….xlsx`; в отчёте только свои ИНН |
| Оба: «Статус», «Отчёт» | Свой статус, свой файл |

Автотест: `test_two_users_each_get_their_own_report` (порядок обработки — по очереди, внешние запросы по каждому ИНН по разу).

## 2. Чужой отчёт недоступен

| Шаг | Ожидание |
| --- | --- |
| Пользователь без проверок: «Статус», «Отчёт» | «Проверок пока нет», «Готового отчёта пока нет» — файла нет |
| Пользователь без проверок: «Проверить ИНН» → ИНН из чужого пакета | Карточка **без** блока «Внутренние данные» |
| Владелец пакета: тот же ИНН | Блок «Внутренние данные» есть; названия из чужих файлов нигде не видны |
| Аккаунт не из списка: любое сообщение | «Доступ к боту ограничен» с ID, больше ничего |

Автотест: `test_a_user_never_sees_another_users_report_status_or_card_data` (плюс прямые вызовы репозитория: `RunNotFound` на чужой проверке).

## 3. Остановка во время анализа

| Шаг | Ожидание |
| --- | --- |
| Запустить проверку с 2+ организациями; пока идёт (`run_started` в логе, уведомления ещё нет) — остановить бота (`Stop-Process` / `systemctl stop`) | Уведомления нет; в логе нет `run_finished` |
| Запустить бота снова | В логе `run_recovered`, затем `run_finished`; пользователю приходит уведомление и отчёт **один раз** |
| В логе | Внешние запросы только по организациям, не сохранённым до остановки (`external_fetch` шаги переиспользуются); модель не спрашивается заново по сохранённым ответам |

Автотест: `test_a_run_interrupted_mid_analysis_is_finished_by_the_next_process` — источник «зависает» на второй организации, задача обработчика убивается, новый процесс на той же БД: `recover` → проверка `completed`, `attempts=2`, внешний запрос только по второй организации.

## 4. Повторная доставка

| Шаг | Ожидание |
| --- | --- |
| «Отчёт» дважды | Тот же файл дважды; новой проверки и новых обращений к источникам/модели нет (`/status` — та же проверка) |
| Сымитировать сбой отправки (например, отключить сеть на секунду и нажать «Отчёт») | «Не удалось отправить файл. Попробуйте ещё раз…»; повтор — файл приходит |

Автотест: `test_report_is_delivered_again_and_a_failed_delivery_is_retried` (`fail_once` транспорта → `failed`-доставка → повтор → `delivered`).
