На 16.09.2026 в официальной документации представлены следующие методы, соответствующие выбранному объёму MVP:

Публичное описание методов подтверждает наличие интерфейсов, но не доступность конкретных данных по ключу заказчика. 16.09.2026 выполнен один проверочный `POST /v2/company` с полученным ключом и ИНН из официального примера: HTTP 200, `meta.status=ok`, ИНН совпал. По полученному ключу проверен только `/v2/company` на текущем подключении. Финансы и ЕФРСБ по ключу ещё не проверены. Точные поля адаптера и условия тарифа подтвердить при интеграции.

### Замер времени на реальных запросах — 21.09.2026

Прогон нашим же адаптером (`CheckoCompanyDataProvider`, три раздела на организацию, последовательно, из Франции, временный ключ разработчика):

| Организация | Время | Разделы |
| --- | --- | --- |
| Крупный банк | 8,0 с | все три ответили; финансовой отчётности нет (для банка это нормальный ответ) |
| Три обычных ООО | 4,7–7,2 с | все три раздела с фактами |
| Несуществующий ИНН | 5,8 с | все три раздела — `not_found` |

Итого 31 секунда на пять организаций: медиана 5,8 с на организацию, максимум 8,0 с. **Оценка на 50 организаций — около 5 минут** при последовательном обходе и 150 запросов к источнику. Сбоев и повторов в этом прогоне не было, хотя раньше отдельные запросы отваливались по таймауту TLS.

Это укладывается в наши собственные лимиты проверки (`RUN_REQUEST_LIMIT = 1500`, `RUN_TIME_LIMIT_SECONDS = 900`) с большим запасом: 150 запросов из 1500 и 5 минут из 15.

**Стоимость.** Тариф бесплатный: `meta.balance` всегда `0.0`, платить не за что. Ограничение не в деньгах, а в количестве: **100 запросов в сутки** (подтверждено владельцем ключа 21.09.2026). В `meta.today_request_count` виден расход за день — этот замер поднял счётчик с 14 до 30.

**Сколько это организаций.** Одна организация стоит **три запроса** (сведения, ЕФРСБ, финансы), а у компании с большим числом сообщений ЕФРСБ добавляется по запросу на каждую следующую страницу. Значит, суточного лимита хватает примерно на **33 организации**, а не на сто. Пакет из 50 организаций за один проход потребует 150 запросов и в бесплатный тариф не уложится: часть разделов вернётся с отказом источника, и в отчёте это будет видно как неполнота, а не как отсутствие риска.

Что с этим делать: для одного пользователя и пакетов до трёх десятков организаций бесплатного тарифа достаточно; для больших пакетов покупается платный тариф, и меняется только значение `CHECKO_API_KEY` — код не трогается. Успешные ответы кэшируются по паре «ИНН + раздел» на `EXTERNAL_CACHE_TTL_SECONDS` (по умолчанию час), поэтому повторный запуск того же списка в пределах часа расход не удваивает.

**Что бот делает, когда лимит кончился (27.09.2026).** Если источник отвечает 429 и после повторов guard'а, проверка перестаёт его спрашивать: следующие организации получают заглушку `source_limit` («Источник данных ответил, что лимит запросов исчерпан; раздел не проверен») без запроса, а итог проверки говорит «Источник данных исчерпал лимит запросов, дальше его не спрашивали; повторите проверку завтра» (`RunSummary.source_limited`). Незаконченные организации не сохраняются, поэтому возобновлённая проверка спросит источник снова. Карточка `/inn` живёт со своим бюджетом и спрашивает заново. **Как Checko сообщает об исчерпании (проверено 27.09.2026, ключ израсходован до конца):** HTTP 403, `meta.status: "error"`, `message: "Превышен суточный лимит запросов для бесплатного тарифа"`, `today_request_count` остаётся на пределе — отклонённые запросы лимит не тратят. Адаптер (#70) различает этот 403 по тексту сообщения (другой 403 остаётся «нет доступа») и отдаёт `RATE_LIMITED` с кодом `daily_limit`; guard такой ответ **не повторяет** — до завтра ничего не изменится — и сразу закрывает источник для остальных организаций проверки.

### Что проверить первым при реализации

1. Доступность трёх методов на выбранном ключе, тариф, квоты и стоимость запросов и страниц.
2. Реальные схемы ответов, коды ошибок и признаки отсутствия данных.
3. Пагинацию сообщений, сортировку по датам, ссылки и идентификаторы событий.
4. Типы сообщений и соответствие юридического лица роли должника; правила отмены, изменения и завершения событий.
5. Доступные годы, единицы финансовых величин и сопоставимость показателей.
6. Условия сохранения, кэширования и показа данных в пользовательском отчёте.

Результат проверки — обезличенные ответы для контрактных тестов и явное отображение полей в доменную модель. До этого демоадаптер использует синтетические доменные факты, а не выдаёт выдуманный JSON за ответ Checko.

### Нормализованный ответ адаптера

Каждый раздел возвращает:

- `source`, `inn`, `fetched_at`, `source_updated_at` при наличии.
- `status`: `ok`, `not_found`, `unavailable`, `rate_limited`, `unauthorized`, `invalid_response`.
- `coverage`: `complete`, `partial` или `unavailable`; причина неполноты/недоступности и охваченный период.
- `facts[]`: идентификатор факта, тип, значение, дата/период, единица измерения.
- `evidence[]`: ID записи источника и проверенный URL, когда они доступны.
- `error`: безопасный код и краткое описание без ключей доступа.

Для неуспешного раздела (`status != ok`) используется `coverage=unavailable` с безопасной ошибкой и без фактов. Проверенная ограниченная выборка — `status=ok, coverage=partial` с причиной пропусков, даже если последующие страницы получить не удалось.

Пустая успешная выборка в известном полном диапазоне отличается от таймаута и отсутствующего раздела. Достижение лимита страниц обязательно даёт `partial`. Отсутствие ссылки не компенсируется придуманным URL: сохраняется доступный идентификатор и название источника.

Адаптер использует HTTPS. Ключ исключается из журналов, сообщений об ошибках и отчётов, включая строки URL. Ответы валидируются до расчёта показателей; неизвестные поля не становятся сигналами автоматически.

## ИИ-провайдер

Провайдер и модель пока не выбраны. При выборе проверить доступность, допустимость обработки данных заказчика, качество русского текста, поддержку выбранной схемы ответа и стоимость на контрольном пакете. Прикладной сценарий зависит от интерфейса `RecommendationProvider`, а не от SDK конкретного поставщика.

Модель получает подготовленные факты и комментарии. Доступ к Checko, БД и Telegram у неё отсутствует. Требования к контексту, валидации и лимитам описаны в [архитектуре](architecture.md).

## Деморежим

Демо- и реальные данные выбираются для всей проверки и помечаются в сводке и отчёте. Сбой реального API никогда не подменяется успешным демоответом. Синтетические примеры не используют реальные сведения о неблагополучии компаний.

## Сетевая доступность — решение 16.09.2026

Пользователь сообщил, что клиент в РФ не может пользоваться Telegram, а сайт Checko из Франции открывается через VPN РФ. Один запрос к API из текущего окружения прошёл, но VPN не переключался: доступ без него и причина ограничений не установлены.

Пользователь решил оставить Telegram-бота; переход на веб не согласован и не входит в работу. При развёртывании планируется прокси. Предлагаемая схема: сервер с российским выходным адресом вызывает Checko напрямую, а Telegram API — через отдельный доступный маршрут/прокси. Конкретный сервер, прокси и их доступность ещё не проверены. Не применять единый глобальный маршрут ко всем запросам: доступ к Checko и Telegram проверяется отдельно.

Прокси бота обеспечивает связь сервера с Telegram API; если приложение Telegram недоступно клиенту, это отдельная проблема доступа на его устройстве. До приёмки развёртывания нужен полный обмен сообщениями с реального устройства клиента. Настройки прокси и секреты хранить вне Git и логов; новую инфраструктуру и оплату без согласования не подключать.

Для разработки остаются офлайн-демосценарии, реальные проверки выполняются отдельно. Клиент Checko и транспорт Telegram должны иметь независимые настройки подключения; реализация прокси относится к этапу серверного развёртывания.
